# SNS 宣传与网店内容

这是内核外的接单配方。现有代码提供本地素材目录盘点；规则草稿和工作手册提供采集、策划、制作、独立检查与人工验收的交接约定。当前由本人手动发布，不连接第三方发布服务，不投稿或排程。Shopify、Canva、CapCut 与只读资料入口仍需分别接入和验收。

## 接入顺序

1. 在私有工作目录建立 `docs/decisions.md`、`docs/declined.md` 和 `connections.md`，登记店铺、账号、素材目录、已核实的工具入口和实际能力。凭据留在服务自己的授权配置中。
2. 用 `assets.example.json` 准备 `assets.json`，只列品牌与营销素材目录，不把财务、客户和合同目录一起扫描。在接单电脑上运行 `node index-assets.ts assets.json inventory.json`。脚本只读媒体文件的路径、大小和修改时间，不读媒体内容、不解压、不跟随符号链接；云盘不可用会失败，不替换上一次结果。元数据相同就保留同一个事件编号，不能用该编号证明媒体内容未变化。
3. 先从各服务的已授权入口读取一次真实资料。Shopify 保存商品及变体、库存口径、价格币种、活动条件和销售汇总；SNS 保存账号、投稿 ID、时间、正文、媒体及可读指标。必须登记分页、覆盖时间与缺失范围。设计稿和本地成品不能证明已经投稿。
4. 分别在后台入口验收 Shopify 只读、Canva 设计读取与导出、CapCut 素材编辑与导出、SNS 历史读取。历史也可以先使用本人给出的链接或导出，记录覆盖范围；不为此接入发布中间服务。聊天中的连接不能替代后台验收。需要浏览器时复用 [browser-handoff](../browser-handoff/README.md)，由实际接单方式验收；不要为后台执行者配置中台 owner MCP。
5. 将本目录手册放入 Agent 的 Skill 目录，名称为 `sns-promotion`，将 `manual-review.template.md` 放到工作目录。`rules.draft.json` 是独立检查用的草稿；替换 worker、可信绝对目录和可用的 Agent 程序后，再合并进现有规则。保留本人已有通道，不新建通道密钥。最后一条规则只整理交付包并交本人验收，收到通过也不自动发布。

## 分工与服务权限

| 职责           | 初始执行工具                   | 所需能力                                                    |
| -------------- | ------------------------------ | ----------------------------------------------------------- |
| 资料采集       | 普通命令、Codex                | Shopify 只读、素材只读、SNS 历史读取                        |
| 策划           | Codex                          | 读取已采集的资料，必要时核对原处                            |
| 图文及视频制作 | Codex 调度工具                 | Canva、CapCut 的选定素材与设计编辑、导出                    |
| 独立检查       | Claude，或本人选定的独立执行者 | 读取最终文案、实际成品及商品事实                            |
| 验收及发布     | 本人                           | 检查交付包，在四个平台手动投稿；Agent只读核对本人提供的链接 |

职责不等于常驻进程，也不要求重复购买订阅。每个执行入口分别配置所需 MCP 工具或官方 API。Skill 和 `access` 不能强制云服务只读；要收窄能力，应使用服务支持的权限或客户端工具清单，并真实验收。不要将本人的 Shopify 完整管理工具默认提供给所有角色。

## 怎么算完成

第一条真实流程要能从最新事实与可用素材生成一套实际成品，独立检查针对确切版本，然后把四个平台的文案、媒体、预览和检查结果交本人手动验收。本人负责手动发布；之后记录本人提供的链接并在只读入口可用时核对。没有发布证据时不能标为已发布。AutoLoop 仍负责队列、并发、复查与问人，配方不另建调度器。

每轮记录本人接受了什么、哪些部分要重做及原因，用于稳定产物质量。只有本人之后另行决定，才评估自动发布；不按通过次数自动开通服务或申请发布权限。

Blog 在 SNS 流程稳定之后扩展：先读取店铺现有文章，使用同一产品事实和素材，生成带来源的文章草稿，由本人验收和手动发布。不把 SNS 简单拼成长文，也不因准备了文章就开启自动发布。

本地测试只使用临时目录，不连接账号、不发消息。真实接入记录应写出接单电脑、启动入口、服务返回的身份、完成的步骤和证据；未验收项保持未验收。

## 可选的 Gemini 原生素材与创意入口

原生Antigravity可按[官方Sidecar接口](https://antigravity.google/docs/sidecars)启动Gemini。`native-sidecar.ts`只在官方原生宿主内调用宿主提供的agentapi，不包装消费账号的agy -p，不读取或转存登录凭据。用Sidecar的agent_permissions只开放本任务资料目录的读取与response.json写入，不把中台owner MCP提供给原生Agent。

先在私有目录的packet/放精选资料与brief.md，再执行：

```bash
node native-task.ts prepare /absolute/private-sns/native creative discord:task-id
```

Sidecar使用`node /absolute/recipe/native-sidecar.ts /absolute/private-sns/native`，按官方文档登记并选择实际原生项目。它只对新请求启动原生会话，回执保留实际Gemini标识、资料摘要和真实产物；具体模型版本未暴露时不编造。原生应用需保持运行。

AutoLoop的command规则调用`node native-task.ts poll /absolute/private-sns/native`，为其登记`emits`允许的`sns.creative.ready`事件，再交给Codex制作。轮询脚本不调用模型，不另建中央队列或重试器。不要在模型进程里等待回执；需要本人恢复连接时交卡片并结束该轮。当前入口一次处理一个活动资料包，未结束前不覆盖它。

首次验收用`verification`代替`creative`。真实原生读写成功后仍不产生制作事件，不能把连接探测当成真实营销产物。自动测试使用临时资料验证回执与事件边界；真实原生会话另留证据。
